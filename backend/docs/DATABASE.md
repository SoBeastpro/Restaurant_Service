# Базы данных микросервисов

## Модель владения

У каждого сервиса своя база, свой пользователь PostgreSQL и своя история Flyway. В локальной среде
они размещены в одном экземпляре PostgreSQL ради экономии ресурсов, но сервис не получает доступ к
базе соседа.

| База | Пользователь | Владелец данных |
|---|---|---|
| `identity_db` | `identity_app` | пользователи, сессии, токены, глобальные роли |
| `restaurant_db` | `restaurant_app` | рестораны, залы, столы |
| `workforce_db` | `workforce_app` | членство, приглашения, ресторанный RBAC |
| `operations_db` | `operations_app` | смены, участники, задачи, шаблоны |
| `billing_db` | `billing_app` | тарифы, подписки |
| `notification_db` | `notification_app` | уведомления, устройства, доставка |
| `audit_db` | `audit_app` | аудит, активность, системные события |
| `reporting_db` | `reporting_app` | денормализованные статистические проекции |

Миграции лежат в `services/<service>/src/main/resources/db/migration`. Нумерация Flyway независима
внутри каждого сервиса.

## Что изменилось по сравнению с общей БД

- удалены схемы-модули одной базы и все межсервисные FK;
- устранён циклический FK между рестораном и членством директора;
- ресторан хранит внешний `director_user_id`, а профиль `DIRECTOR` создаёт workforce-сценарий;
- определения ресторанных ролей и permissions полностью принадлежат `workforce-service`;
- глобальные платформенные роли принадлежат `identity-service`;
- каждый изменяющий состояние сервис получил собственный `outbox_events`;
- каждый потребитель событий получил `inbox_messages`;
- статистика вынесена в отдельную eventually-consistent read-модель.

Внешний UUID не подтверждает существование сущности на уровне PostgreSQL. Эту гарантию даёт
команда приложения: проверка локальной проекции или внутреннего API и запись изменения с outbox в
одной транзакции.

## Локальный запуск

```bash
cd backend
docker compose up -d postgres
```

Примеры подключения:

```bash
docker compose exec postgres psql -U identity_app -d identity_db
docker compose exec postgres psql -U operations_app -d operations_db
```

Пароли локального окружения совпадают с коротким именем сервиса (`identity`, `operations` и т. д.).
Они предназначены только для разработки.

## Старый локальный том

PostgreSQL выполняет `/docker-entrypoint-initdb.d` только при создании пустого тома. Если старые
данные нужны, сначала сделайте дамп. Для чистого локального старта можно сознательно выполнить:

```bash
docker compose down -v
docker compose up -d postgres
```

Эта команда необратимо удаляет только локальный docker-том проекта. Не запускайте её, если в томе
есть нужные данные.

## Применение миграций

После создания Java-сервисов каждый сервис запускает только собственный Flyway location и
подключается только своим пользователем. Gateway не запускает миграции и не имеет базы.

Для production допускается один управляемый PostgreSQL-кластер с разными базами/ролями на первом
этапе. Позже любой сервис можно перенести в отдельный кластер без изменения его API и идентификаторов.
