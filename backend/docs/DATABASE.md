# База данных REST Restaurant

База данных представляет собой чистую основу для модульного монолита. Таблицы приложения не
хранятся в схеме `public`: в ней находятся только история Flyway и общая функция
`set_updated_at`.

Визуальная схема и все связи между сущностями описаны в [ERD.md](ERD.md).

## Модули

| Схема PostgreSQL | Назначение и данные |
|---|---|
| `identity` | Глобальные пользователи, ресторанные и платформенные роли, права, устройства, сессии и токены восстановления |
| `restaurant` | Рестораны, залы, столы и история состояний столов |
| `workforce` | Сотрудники ресторанов, приглашения и индивидуальные переопределения прав |
| `operations` | Смены, посещаемость, задачи, шаблоны, решения о переносе задач и отчёты |
| `billing` | Тарифные планы и условные подписки ресторанов |
| `notification` | Уведомления, регистрация push-устройств, попытки доставки и исходящая очередь событий |
| `audit` | Действия пользователей, неизменяемый аудит с разграничением областей и системные события |

Межмодульные внешние ключи при необходимости используют одновременно идентификатор сущности и
`restaurant_id`. Это не позволяет назначить сотрудника, смену, задачу или шаблон из другого
ресторана.

## Роли и права доступа

Ресторанные роли: `EMPLOYEE`, `MANAGER` и `DIRECTOR`. Они принадлежат записи
`workforce.restaurant_members`, поэтому один глобальный пользователь может иметь разные роли в
разных ресторанах. Частичный уникальный индекс и отложенное ограничение директора гарантируют,
что у каждого ресторана есть только один неархивный директор.

`SYSTEM_ADMIN` — глобальная платформенная роль. Она хранится в
`identity.user_platform_roles` и не является членством в ресторане.

RBAC-матрица прав по умолчанию хранится в таблицах:

- `identity.permissions`;
- `identity.restaurant_role_permissions`;
- `identity.platform_role_permissions`.

Индивидуальные изменения прав сотрудника, менеджера или директора хранятся как `GRANT` или `DENY`
в `workforce.member_permission_overrides`. Представление
`workforce.effective_member_permissions` объединяет права роли с индивидуальными
переопределениями. Мета-права, позволяющие изменять права других пользователей, нельзя назначать
индивидуально.

Правила авторизации в приложении:

- менеджер может изменять права только сотрудников;
- директор может изменять права сотрудников и менеджеров своего ресторана;
- системный администратор может изменять права директоров;
- разрешать и запрещать можно только существующие права.

При записи индивидуальных переопределений бэкенд должен проверять иерархию ролей и в той же
транзакции добавлять соответствующую запись в `workforce.member_permission_history`.

## Бизнес-состояния

Состояния столов: `READY`, `NEEDS_CLEANING`, `NEEDS_SERVING` и `PROBLEM`. Цвет интерфейс определяет
на стороне клиента, в базе данных он не хранится. Для состояния `PROBLEM` обязателен непустой
комментарий.

Состояния смен: `PLANNED`, `ACTIVE`, `CLOSED` и `CANCELLED`. В ресторане одновременно может быть
активна только одна смена. Для соответствующих состояний обязательны фактические даты начала и
закрытия, а также сотрудники, выполнившие эти действия.

Состояния задач: `CREATED`, `IN_PROGRESS`, `COMPLETED` и `CANCELLED`. Просроченность вычисляется по
`due_at` и не хранится как отдельное состояние. `carry_over_state = PENDING` означает неназначенную
задачу, ожидающую следующую смену. Решения, принятые при закрытии смены, сохраняются в
`operations.shift_task_resolutions`.

## Условная подписка

Подписки принадлежат ресторанам. Тариф `MONTHLY_PLACEHOLDER` действует 30 дней и имеет нулевую
стоимость. Нажатие кнопки-заглушки оплаты должно активировать или продлить подписку и добавить
событие `ACTIVATED` или `EXTENDED`. Платёжные транзакции, возвраты и споры пока намеренно не
моделируются.

## Порядок миграций

Рабочие миграции выполняются в следующем порядке:

1. схемы модулей и общая функция;
2. модуль идентификации и определения RBAC;
3. структура ресторанов;
4. сотрудники и индивидуальные права;
5. смены и задачи;
6. подписки;
7. уведомления и исходящая очередь событий;
8. аудит;
9. каталог прав RBAC и значения по умолчанию.

`db/demo/V10__seed_modular_demo_data.sql` загружается только тогда, когда
`classpath:db/demo` добавлен в `FLYWAY_LOCATIONS`. Не подключайте этот путь вне локальной среды
разработки.

## Локальное пересоздание

Следующая команда удаляет существующий локальный том PostgreSQL вместе со всеми данными:

```bash
docker compose down -v
docker compose up -d postgres redis rabbitmq
SPRING_JPA_HIBERNATE_DDL_AUTO=none ./mvnw clean spring-boot:run
```

Подключение к PostgreSQL:

```bash
docker compose exec postgres psql -U rest -d rest
```

Полезные проверки:

```sql
SELECT version, description, success
FROM public.flyway_schema_history
ORDER BY installed_rank;

SELECT schemaname, tablename
FROM pg_tables
WHERE schemaname IN (
    'identity', 'restaurant', 'workforce', 'operations',
    'billing', 'notification', 'audit'
)
ORDER BY schemaname, tablename;

SELECT member.role_code, permission.permission_code
FROM workforce.restaurant_members member
JOIN workforce.effective_member_permissions permission
  ON permission.membership_id = member.id
ORDER BY member.role_code, permission.permission_code;
```
